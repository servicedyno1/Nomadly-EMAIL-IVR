## Determination
The INVALID-signature log fires only when `sigState === 'invalid'`; the SIGDEBUG
diagnostic also fires only on invalid (debug flag off). Both went silent across the
deploy boundary while the secret stayed set and DynoPay kept signing (pre-fix these
same webhooks carried a header — you cannot be "invalid" without one).

➡️ **The secret now validates in production — the multi-`v1` rotation fix worked.**
Pre-fix: 100% INVALID. Post-fix: 0% INVALID, store handler confirmed running.

### Residual ambiguity (small)
Absence of the INVALID line means `sig` is either `valid` (expected) or `unsigned`
(only if DynoPay sent these particular deliveries with no header). Pre-fix the same
per-payment deliveries WERE signed, so `valid` is by far the likely reading, but we
have no explicit positive `sig=valid` line yet because the only post-fix DynoPay
webhooks were WALLET deposits (store path exits at "no matching order" before the
`decision=… sig=…` log).

To close this to 100%: set `DYNO_PAY_WEBHOOK_SIG_DEBUG=true` in prod for a short
window → the next webhook logs `[Store][SIGDEBUG] {hasV2, matchedScheme, …}`
(fires on every webhook, valid or not), then turn it back off. Or wait for the next
real STORE-ORDER webhook and read its `decision=… sig=valid` line.

## Enforcement recommendation
Do NOT flip `DYNO_PAY_WEBHOOK_SIG_ENFORCE=true` yet. Evidence is strong but based on
the absence-of-INVALID across a single post-fix payment. Confirm `sig=valid`
explicitly (diagnostic toggle or next store-order webhook) over a few deliveries
first — enforcing prematurely would 401-reject webhooks during any future rotation
window and could drop real payments.
